# 0002. 리뷰는 미리 만든 내용 주소 집계 스냅샷에서 읽는다

- 상태: 채택
- 범위: H&M 가격·연령 자료, 원단 판매 목록 참고값

## 맥락

H&M 자료는 고객 CSV 하나와 거래 행이 수천만 개인 Parquet 둘로 이루어집니다. 요청마다 집계하면 수십 초가 걸렸고 1.5 GB 컨테이너에서 메모리가 모자랐습니다([T-DATA-01](../troubleshooting.md#t-data-01-컨테이너에서-연령-집계가-메모리-부족으로-실패)). 리뷰에 필요한 차원(카테고리, 상품 세그먼트, 상품 유형, 연령대)은 정해져 있고 많지 않습니다.

## 결정

- 오프라인 빌더가 집계를 한 번 실행해 연령대 프로필, 가격 통계, 크기가 제한된 원단 판매 목록 CSV를 JSON 객체 하나에 담습니다.
- 객체 키는 스냅샷 내용의 SHA-256입니다. 빌더는 같은 키에 다른 객체가 있으면 덮어쓰지 않습니다.
- 스냅샷은 원본 객체 버전과 카테고리 매핑의 SHA-256을 기록합니다. 서비스는 자기 매핑 지문과 다른 스냅샷을 거부합니다.
- 스냅샷 키가 설정되면 서비스는 프로세스마다 그 객체를 한 번 읽어 캐시합니다. 읽기나 검증에 실패하면 세 자료원을 모두 오류로 알리고, 원본 객체를 훑는 방식으로 **되돌아가지 않습니다**.

## 결과

- 요청은 차가운 프로세스에서 객체 한 번, 그 뒤에는 0번 읽습니다.
- 미리 계산한 차원만 쓸 수 있습니다. 새 차원이나 매핑 변경에는 재빌드와 설정 변경이 필요합니다.
- 자동 대체가 없으므로 스냅샷이 깨지면 가용성이 떨어지지만, 서로 다른 자료나 매핑으로 만든 수치가 한 리뷰에 섞이지는 않습니다.
- 캐시가 프로세스마다 있어 복제본이 많으면 사본도 많아집니다.

## 검토한 대안

- **요청마다 원본 객체를 조회합니다.** 스냅샷 키가 없을 때의 개발 모드로 남겼습니다. 요청 경로로 쓰기에는 느리고 메모리를 많이 씁니다.
- **웨어하우스나 PostgreSQL 구체화 뷰.** 임의 차원이나 잦은 갱신이 필요하면 낫지만, 바뀌지 않는 과거 데이터셋을 위해 늘 켜 둔 데이터베이스가 생깁니다.
- **원본 객체로 자동 대체.** 버전·매핑·기간이 섞이지 않게 하는 계약 없이는 택하지 않습니다.
