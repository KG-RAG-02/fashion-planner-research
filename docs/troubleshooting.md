# 문제 해결과 교훈

research 서비스를 만들며 겪은 문제를 원인, 해결, 다시 쓸 교훈과 함께 정리합니다. 항목마다 증상, 원인(근거), 해결, 검증, 교훈, 커밋 순서로 적습니다.

영역: `DATA`(H&M 집계와 스냅샷), `MAP`(카테고리 매핑), `DEP`(의존성), `COST`(원단 원가), `PKG`(패키징), `LLM`(타깃 가설), `HTTP`, `OPS`(컨테이너), `CFG`(설정), `BUILD`(이미지), `TEST`.

## T-DATA-01 컨테이너에서 연령 집계가 메모리 부족으로 실패

- **증상.** 통합 Docker 환경(메모리 1.5 GB, 읽기 전용 루트 파일시스템)에서 리뷰마다 20–30초를 쓰고 `CUSTOMER_AGE_RESEARCH_FAILED`(`stage=duckdb_httpfs_and_aggregate`, `code=OutOfMemoryException`)로 끝났습니다. 그 전에는 같은 쿼리가 `Failed to create directory ".tmp": Read-only file system`으로 실패했습니다. 한도를 3 GB, 4 GB로 올려도 `OutOfMemoryException`이 났습니다.
- **원인.** 원격 쿼리 하나가 `httpfs`로 거래 Parquet을 훑으면서 상품·고객과 조인하고 그룹별 고유 고객 수를 한꺼번에 셌습니다. Parquet 스캔 버퍼와 고유 개수 해시 상태가 동시에 정점에 이르렀습니다. 또 DuckDB의 기본 임시 디렉터리가 상대 경로(`.tmp`)라 읽기 전용 루트에서 만들 수 없었습니다.
- **해결.**
  1. 집계 연결마다 스레드 수(기본 1), 메모리 한도, 캐시 볼륨 아래의 절대 경로 임시 디렉터리를 직접 지정합니다(`_configure_age_duckdb`).
  2. 거래·상품·고객 입력을 임시 테이블로 먼저 만든 뒤 조인해, 스캔과 고유 개수 계산이 겹치지 않게 합니다.
  3. 무거운 쿼리를 요청 경로에서 뺍니다. 집계 스냅샷을 오프라인에서 만들고 요청은 그것을 읽습니다(프로세스마다 객체 1회 읽기).
- **검증.** 같은 이미지·1.5 GB 한도의 일회성 컨테이너에서, 스레드를 줄이고 `preserve_insertion_order=false`를 준 쿼리는 39.6초에, 두 단계로 나눈 쿼리는 27.7초에 성공했고 두 결과의 정규화 해시가 같았습니다. 단위 테스트 `test_duckdb_memory_parallelism_order_and_spill_are_bounded`가 연결 설정을 고정합니다.
- **교훈.** 큰 과거 데이터는 요청 경로 밖에서 미리 집계합니다. 컨테이너에서는 호스트 기준 기본값을 믿지 말고 DuckDB의 스레드, 메모리 한도, 절대 경로 임시 디렉터리를 직접 정합니다.
- **커밋.** {{commit:73ed40a}}, {{commit:571a558}}

## T-DATA-02 카테고리 매핑을 바꾼 뒤 기존 스냅샷이 거부됨

- **증상.** 버킷에 있던 스냅샷을 쓸 수 없게 됐습니다. 가장 오래된 것은 `Aggregate snapshot schema is invalid.`로, 그 뒤 것들은 프로필을 고르는 단계에서 실패했습니다.
- **원인.** 스냅샷은 스키마 버전과, 만들 때 쓴 카테고리 매핑의 SHA-256을 기록합니다. 매핑에 한국어 별칭이 추가되며 지문이 달라졌습니다. 의도한 동작입니다. 서로 다른 매핑으로 만든 집계를 섞으면 한 카테고리가 가리키는 상품 범위가 몰래 바뀝니다.
- **해결.** 현재 매핑으로 스냅샷을 새로 만듭니다. 키가 내용 해시라서 새 스냅샷은 새 키를 받고, 옛 객체는 그대로 남습니다.
- **검증.** `test_runtime_rejects_retired_aggregate_snapshot_schema`와 스냅샷 읽기의 매핑 지문 검사.
- **교훈.** 파생 데이터는 입력(원본 객체 버전, 매핑 해시, 쿼리)으로 식별하고, 다르면 닫힌 쪽으로 실패하게 합니다. 재빌드 방법은 매핑 파일 가까이에 적어 둡니다.
- **커밋.** {{commit:d658b65}}, {{commit:73ed40a}}

## T-MAP-01 실데이터 리뷰가 모두 `no_results`

- **증상.** 실제 H&M 자료를 연결하자 리뷰가 `No H&M source category mapping targets the requested category`와 함께 `no_results`를 냈습니다.
- **원인.** 앞 단계 초안은 `스커트` 같은 한국어 카테고리를 쓰는데, H&M 매핑은 `Bottoms`, `Knitwear` 같은 영어 카테고리를 가리켰습니다. 두 어휘를 잇는 것이 없었습니다.
- **해결.** 한국어 이름을 H&M 카테고리로 잇는 명시적 별칭 표를 만들고, 나중에 `스커트`, `가디건`, `팬츠` 같은 소분류까지 카테고리 매핑 파일 안(`requested_category_aliases`)으로 옮겼습니다.
- **검증.** `test_korean_category_alias_selects_hm_knitwear_snapshot_profile`, `test_korean_tops_category_selects_real_tops_price_and_customer_aggregates`.
- **교훈.** 서비스 경계에서 어휘를 버전이 있는 명시적 표로 맞추고, 추측하지 말고 어떤 별칭을 적용했는지 응답에 남깁니다.
- **커밋.** {{commit:98e6351}}, {{commit:d658b65}}

## T-DEP-01 DuckDB 1.x가 DuckDB 2.0 파일을 열지 못함

- **증상.** 캐시를 미리 받는 단계에서 버킷의 DuckDB 데이터베이스 객체를 열다가 `IOException`이 났습니다.
- **원인.** 객체는 DuckDB 2.0 저장 형식으로 쓰였는데, 설치된 DuckDB는 1.5.6이었습니다.
- **해결.** `r2` extra에서 `duckdb>=2,<3`을 요구합니다. 컨테이너 이미지는 빌드 때 맞는 `httpfs` 확장을 설치하므로, 요청 중에는 확장을 설치하지 않습니다.
- **검증.** Python 3.14, DuckDB 2.0.0에서 단위 테스트가 통과했습니다.
- **교훈.** 저장 형식을 가진 라이브러리는 데이터를 쓴 주 버전에 고정하고, 확장은 이미지 빌드 때 설치합니다.
- **커밋.** {{commit:ad8bd54}}

## T-COST-01 판매 목록 가격이 생산 원가처럼 읽힐 수 있음

- **증상.** 리뷰 응답에 `fabric_cost_analysis.unit_cost`와 `verified_price_per_meter_available`가 남아 있어, 받는 쪽이 검증된 소재 원가로 오해할 수 있었습니다.
- **원인.** 미터당 값은 공개 판매 목록에서 오거나, 판매 단위 길이만 있을 때 가격을 그 길이로 나눈 값입니다. 참고값이지 조달 원가가 아닙니다.
- **해결.** 두 필드를 응답 투영에서 빼고, 대신 추정 방법(`method`)을 보여 줍니다. 검증된 근거가 없으면 `decision_support.evidence_areas.material_cost`는 false로 남습니다.
- **검증.** `tests/test_http_server.py`가 응답에 `unit_cost`와 `verified_price_per_meter_available`가 없는지 확인합니다.
- **교훈.** 추정값은 계약에서도 추정값으로 이름 붙이고, 실제보다 확실해 보이게 하는 필드는 지웁니다.
- **커밋.** {{commit:0b3bc53}}

## T-PKG-01 카테고리 매핑 사본 두 개가 어긋남

- **증상.** 패키지 안의 카테고리 매핑 사본은 1.1에 머물러 한국어 별칭 11개가 없었고, 원본 사본은 이미 1.2였습니다.
- **원인.** 설정과 프롬프트가 레포 루트와 패키지 안에 두 벌 있었고, 수동 스크립트로 맞췄습니다.
- **해결.** 사본을 맞췄고, 공개본에서는 패키지 `resources/`만 남겼습니다.
- **검증.** 공개 기준선에서 루트 사본을 지우기 전에 두 사본을 바이트 단위로 비교해 차이가 없음을 확인했습니다.
- **교훈.** 실행에 쓰는 자산은 한 곳에만 두고 `importlib.resources`로 읽어, 소스 체크아웃·휠·이미지가 같은 바이트를 읽게 합니다.
- **커밋.** {{commit:378b3dc}}

## T-LLM-01 사소한 모양 차이로 타깃 가설 전체가 실패

- **증상.** 리뷰가 가끔 `TARGET_AUDIENCE_LLM_FAILED`를 내며 타깃 고객 가설 전체를 잃었습니다.
- **원인.** 검증기가 `secondary_segments`를 문자열 1–2개의 목록으로만 받았는데, 모델이 문자열 하나나 3개 이상을 돌려줄 때가 있었습니다.
- **해결.** 그 필드만 정규화합니다(문자열은 항목 하나짜리 목록으로, 3개 이상은 2개로 자르고, 비면 중립 문구). 다른 필드가 틀린 출력은 계속 거부합니다.
- **검증.** `tests/test_target_audience_cache.py`가 정규화를 확인합니다.
- **교훈.** 안전하게 맞출 수 있는 모양 차이와 거부해야 할 의미 오류를 구분합니다.
- **커밋.** {{commit:571a558}}

- **교훈.** 상태 점검은 상수가 아니라 실제로 관찰한 모드를 알려야 합니다.

## T-HTTP-02 리뷰 경로에 다른 메서드를 보내면 404나 HTML 501

- **증상.** POST 전용 경로에 `GET`을 보내면 `404 NOT_FOUND`가, `PUT`, `DELETE`, `PATCH`, `OPTIONS`, `HEAD`, `TRACE`를 보내면 표준 라이브러리의 HTML 501 페이지가 왔습니다.
- **원인.** 처리기에 그 메서드들의 `do_<METHOD>`가 없었습니다.
- **해결.** 그 경로의 다른 메서드에는 인증보다 먼저 `405`와 `Allow: POST`로 답합니다.
- **검증.** `tests/test_http_server.py`가 메서드마다 `405`와 `Allow: POST`를 확인합니다.
- **교훈.** 프로토콜 오류는 상태 코드를 의도적으로 정합니다. 프레임워크 기본값은 제각각인 본문을 흘립니다.
- **커밋.** {{commit:8d39138}}

## T-OPS-01 64 MB tmpfs가 DuckDB 캐시에 너무 작음

- **증상.** DuckDB 객체 키를 설정하자 캐시 내려받기가 실패했습니다.
- **원인.** 로컬 Compose 프로필이 캐시 디렉터리를 64 MB tmpfs로 붙였는데, 캐시 파일은 최대 2 GB였습니다.
- **해결.** 캐시에는 이름 있는 볼륨을 붙이고 `/tmp`만 tmpfs로 둡니다.
- **검증.** Compose 프로필을 검토했습니다. 이미지 자체는 바뀌지 않았습니다.
- **교훈.** 임시 저장소 크기는 평소 크기가 아니라 담아야 할 가장 큰 객체로 정합니다.
- **커밋.** {{commit:0172690}}

## T-CFG-01 빈 환경변수가 기본값을 덮어씀

- **증상.** 저장 경로 변수를 빈 값으로 두자 기본 경로 대신 현재 디렉터리에 상태가 쓰였습니다.
- **원인.** `os.getenv(name, default)`는 설정됐지만 빈 변수에 `""`를 돌려줍니다.
- **해결.** 빈 값은 설정하지 않은 것으로 봅니다. 지금의 설정 함수도 같은 규칙을 따릅니다.
- **검증.** 정책 변수를 빈 값으로 두면 기본값이 나오는지 단위 테스트가 확인합니다.
- **교훈.** Compose 파일은 `${VAR:-}`처럼 빈 값을 자주 넘깁니다. 빈 값은 "설정 안 함"으로 읽습니다.
- **커밋.** {{commit:e49b09c}}

## T-OPS-02 SQLite 연결이 닫히지 않음(지금은 없는 기능)

- **증상.** Python 3.14가 테스트 중 `ResourceWarning: unclosed database`를 냈습니다.
- **원인.** `with sqlite3.connect(...) as db`는 commit이나 rollback만 하고 연결을 닫지 않습니다.
- **해결.** 연결을 `contextlib.closing()`으로 감쌌습니다. 이 재생 저장소는 나중에 현재 리뷰 계약으로 옮기면서 없앴습니다.
- **교훈.** sqlite3의 context manager는 트랜잭션을 다룰 뿐 연결을 닫지 않습니다.
- **커밋.** {{commit:25ac52a}}

## T-HTTP-03 개정 충돌을 계약 오류로 알림(지금은 없는 기능)

- **증상.** 이미 다른 내용으로 검토한 초안 개정을 다시 보내면 `422`가 왔습니다.
- **원인.** 상태 충돌을 계약 위반 코드로 알렸습니다.
- **해결.** 별도 오류 코드와 함께 `409`를 돌려주고, `422`는 잘못된 입력에만 씁니다. 이 경로는 나중에 재생 저장소와 함께 없앴습니다.
- **교훈.** `422`는 입력의 의미 오류에, `409`는 상태 충돌에 씁니다.
- **커밋.** {{commit:0c5dddf}}

## T-BUILD-01 이미지가 Git에 없는 파일을 복사함

- **증상.** 깨끗한 체크아웃에서 `docker build`가 실패했습니다.
- **원인.** Dockerfile이 개발자 컴퓨터에만 있던 생성 디렉터리 `examples/`를 복사했습니다. 비슷한 문제가 하나 더 있었습니다. 실행 이미지가 `scripts/`와 `tests/`도 복사했습니다.
- **해결.** 실행에 필요한 것만 복사하고, 테스트는 별도 빌드 단계에서 돌립니다.
- **교훈.** 이미지는 CI에서 깨끗한 클론으로 빌드해 봅니다.

## T-TEST-01 테스트가 무시 목록의 생성 픽스처에 기댐

- **증상.** 깨끗한 체크아웃마다 테스트 6개가 `tests/fixtures/` 아래 파일에 대한 `FileNotFoundError`로 오류를 냈습니다.
- **원인.** 그 픽스처는 이미 사라진 스크립트가 만들던 것이었고 `.gitignore`에 들어 있었습니다.
- **해결.** 해당 테스트는 없앤 코드 경로에 속해 함께 지웠습니다. 남은 테스트는 합성 데이터를 메모리에서 만듭니다.
- **교훈.** 테스트는 읽는 것을 모두 스스로 만들거나 커밋해 둡니다.

## T-TEST-02 정책 스위치 테스트가 엉뚱한 이유로 통과

- **증상.** 스위치가 기본으로 켜져 있었는데도 `test_noncommercial_gate_must_be_explicit`가 통과했습니다.
- **원인.** 저장소 자격 증명이 없어 자료원이 설정 오류로 먼저 실패했고, 그 예외가 테스트가 기대한 예외와 같았습니다.
- **해결.** 가짜 저장소 클라이언트를 넣고 스위치 자체를 검사합니다.
- **교훈.** 실패를 검사할 때는 예외 종류만이 아니라 구체적인 이유를 확인합니다.
